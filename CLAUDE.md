# smartmontools-next — Project Instructions

## Project Overview

RPM packaging of the smartmontools trunk (upstream `main`) for the
[karellen/smartmontools-next](https://copr.fedorainfracloud.org/coprs/karellen/smartmontools-next/) COPR project.
This is **not** a PyBuilder project. The package is `smartmontools-next` (plus `smartmontools-next-selinux`),
which `Conflicts`/`Provides` the distribution `smartmontools`.

The packaging is the Fedora dist-git `smartmontools` packaging adapted to the trunk. **This repository shares git
history with Fedora dist-git** (`https://src.fedoraproject.org/rpms/smartmontools.git`); the fork point is Fedora
commit `9d77964` (2023-05-03).

## Repository Layout

```
smartmontools/                # Git submodule -> github.com/smartmontools/smartmontools, branch main
smartmontools-next.spec       # The spec (Fedora's smartmontools.spec, renamed and adapted)
smartmon.te / .if / .fc       # SELinux policy module (from Fedora, see "SELinux" below)
smartdnotify                  # smartd_warning.d notification script (from Fedora)
smartmontools.sysconf         # /etc/sysconfig/smartmontools (from Fedora)
smartmontools.tmpfilesd       # tmpfiles.d entry for /var/lib/smartmontools (from Fedora)
smartmontools-5.38-defaultconf.patch  # Fedora patch, rebased to the trunk layout (src/smartd.conf)
dist-version.sh               # Generated by upstream getversion.sh -s; never edit by hand
.tito/                        # tito config; custom tagger in .tito/libs/karellen/tito/version_tagger.py
.github/workflows/update.yml  # Cron: bump submodule, regenerate dist-version.sh, tito tag, push (every 6h)
tests/tests-DSP.yaml          # Fedora CI SELinux policy test definition (from Fedora)
```

## Build and Release Flow

1. `update.yml` runs every 6 hours. If upstream `main` moved, it updates the submodule, regenerates
   `dist-version.sh` with `util/getversion.sh -s` (falls back to `src/getversion.sh` for the old layout), commits
   `Update <timestamp>`, runs `tito tag --accept-auto-changelog` and `git push --follow-tags`.
2. The COPR package (SCM source, `master`, tito build method, auto-rebuild) builds the pushed tag. It is
   triggered by a GitHub webhook subscribed to `create` events only, i.e. by the creation of the tito tag.
   COPR makes a single SRPM and rebuilds it in every chroot (Fedora 43+/rawhide, RHEL/EPEL/CentOS Stream
   8-10, AlmaLinux 9-10/Kitten, Amazon Linux 2023; x86_64 and aarch64).
3. Versioning comes from `SmartmontoolsVersionTagger`: `<last AC_INIT version in configure.ac>.<commits since
   that configure.ac change>`. `Release` is reset to `1` on every version bump.

### Rules

- **Work on `master` directly.** COPR only builds `master`, so a feature branch cannot be tested.
- **Packaging-only change without a submodule bump:** bump the release only, so the version stays and the
  tag stays unique: `tito tag --use-release=<N>` (the tagger recomputes the version from the submodule, which
  is unchanged), then `git push --follow-tags origin` as tito instructs.
- **Never push more than three tags at once.** GitHub does not generate `create` events "when more than three
  tags are created at once", so COPR is never notified and does not build. Before `git push --follow-tags`,
  make sure no stray local tags are reachable from `master` (see the `--no-tags` fetch below). If a build was
  not triggered, launch it manually in COPR.
- A push without a new tag (e.g. a docs-only commit) does not trigger a COPR build.
- The bot commits to `master` every 6 hours; fetch/pull before committing and pushing.
- `drivedb.h`, `sources` and Fedora's version-specific backport patches are intentionally not carried: the trunk
  already contains them, and the drivedb refresh is not used.

## Synchronizing with Fedora

The packaging follows the Fedora `f44` dist-git branch. Last synchronized Fedora commit: `d433214`.

```bash
git clone https://src.fedoraproject.org/rpms/smartmontools.git .claude-tmp/fedora-smartmontools
git fetch --no-tags .claude-tmp/fedora-smartmontools 'refs/remotes/origin/*:refs/fedora/*'
git log --oneline <last synced Fedora commit>..refs/fedora/f44
git merge --no-commit refs/fedora/f44
```

- **Always fetch with `--no-tags`.** Fedora has dozens of CVS-era annotated tags (`F-*-split`, `FC-*-split`,
  `smartmontools-5_*`) pointing into the shared history; a plain fetch imports them, and tito's
  `git push --follow-tags` then pushes them all, which suppresses the COPR webhook (see Rules above).

- Non-spec files (`smartmon.*`, `smartdnotify`, `smartmontools.sysconf`, `smartmontools.tmpfilesd`) merge normally.
- `smartmontools.spec` -> `smartmontools-next.spec` is **not** rename-detected (the tito changelog makes the
  files too different), so the merge reports a modify/delete conflict. Keep `smartmontools.spec` deleted and
  **port Fedora's spec changes by hand**: diff the Fedora spec between the previous sync point and the branch
  tip (excluding `%changelog`) and apply the relevant hunks to `smartmontools-next.spec`.
- Keep `drivedb.h`, `sources` and Fedora backport patches deleted (check that the trunk contains the backport).
- Fork-specific spec parts to preserve: `%{packagename}`/`-next` naming, `Conflicts`/`Provides`, Vendor/Packager,
  `pushd smartmontools`, the `dist-version.sh` copy, the trunk doc list (`doc/...`), `%{_includedir}/smartmon` and
  `%{_libdir}/libsmartmon*`, and the `libtool`/`gpg` BuildRequires.

## SELinux

Fedora develops the policy against Fedora's base policy only, but the same module is built for every COPR
chroot. Local change carried on top of Fedora: the `pidfs_t` rule in `smartmon.te` is wrapped in
`optional_policy(` + `gen_require(` because `pidfs_t` does not exist in the EL8, EL9 and Amazon Linux 2023 base
policies. A missing type does **not** fail compilation, only module installation (linking), so after any
policy change verify by **installing** the module (`semodule -n -s targeted -i smartmon.pp`) in containers with
each distribution's `selinux-policy-targeted`, not just by building it.

## Testing Changes

COPR builds only tags on `master`, so test locally before committing:

1. Build an SRPM from the working tree with the same layout tito's `SubmoduleAwareBuilder` produces
   (`smartmontools-next-<version>/` containing the repository files and the submodule contents), with the spec
   sources next to it in `SOURCES/`, then `rpmbuild -bs --define "_topdir <dir>" smartmontools-next.spec`.
2. Rebuild it with mock in a representative set of chroots, e.g. `fedora-44-x86_64`, `almalinux-8-x86_64`,
   `almalinux-9-x86_64`, `almalinux-10-x86_64`, `amazonlinux-2023-x86_64`.
3. Install the resulting RPMs in clean podman containers of the same distributions and check that
   `%post selinux` loaded the module (`semodule -l`), file contexts resolve (`selabel_lookup -b file -k <path>`),
   and `smartctl --version` runs.

Use the project-local `.claude-tmp/` for scratch files.
